
# 常见项目架构

非常好的问题 👍。  
“分层架构乱掉” 是很多项目在中后期都会出现的典型问题，其实并不是你不会分层，而是**没有统一的分层模式参照**。  
下面我整理出业内常见的**分层架构模式（Layering Patterns）**，帮助你建立一个稳定的参考框架。

---

## 🧩 一、常见的分层架构模式

|模式名称|典型层次|特点|适用场景|
|---|---|---|---|
|**传统三层架构 (3-tier)**|表现层 → 业务逻辑层 → 数据访问层|简单清晰，职责分离|Web / 桌面软件|
|**五层架构 (5-layer system)**|应用层 → 决策层 → 功能层 → 执行层 → 支撑层|面向机器人/嵌入式系统，符合“从任务到执行”逻辑|机器人 / 自动驾驶 / IoT|
|**垂直领域分层 (Vertical slice)**|每个业务独立成一条垂直链，内部再含子层|强化领域独立性|大型系统 / 微服务|
|**管道与过滤器 (Pipeline & Filter)**|数据流通过一系列处理环节（滤波器）|强调数据流处理和顺序|传感器处理、信号处理、AI推理|
|**事件驱动分层 (Event-driven)**|事件源 → 事件处理层 → 反应层|异步反应快，模块松耦合|控制系统 / 机器人行为管理|
|**六边形架构 (Hexagonal / Port & Adapter)**|核心逻辑层 ←→ 适配层（输入/输出端口）|提高可测试性、易于换接口|ROS节点、BCI/MR接口等场景|
|**分布式部署架构 (Distributed layering)**|设备层 → 边缘计算层 → 云层 → 交互层|强调跨设备分布与通信|多机协作 / MR / 云控机器人|

---

## 🧭 二、机器人/控制系统常用的分层逻辑（推荐你使用的框架）

这是与你项目（底盘 + 机械臂 + BCI/MR）最契合的一种模式，也就是你在《架构模板.md》中已经部分采用的 **五层架构**：

|层级|职责|示例模块|
|---|---|---|
|**应用层**|定义任务目标、交互接口、人机协作|BCI/MR、任务规划|
|**决策层**|做出行为决策与路径规划|行为树、Nav2 Planner、任务调度|
|**功能层**|感知环境、构建地图、避障控制|SLAM、感知融合、控制算法|
|**执行层**|将控制指令转化为运动或动作|底盘、电机驱动、机械臂控制|
|**支撑层**|通信、操作系统、中间件、仿真|ROS2、DDS、Gazebo、服务器|

👉 这套分层方式的优点是：

- **符合物理执行链路**（感知 → 决策 → 执行 → 反馈）；
    
- **易于映射到团队分工**（软件、电子、机械）；
    
- **可拓展性强**（上接BCI/MR，下接底盘控制）。
    

---

## ⚙️ 三、为什么会“乱分层”

你提到“有时候叫模块架构、有时候叫功能架构”，这正是因为：

- **分层维度混用**（按“功能”分 vs. 按“结构”分）；
    
- **文档目标不一致**（一会儿想描述功能关系，一会儿又想说明模块职责）；
    
- **命名缺乏统一视角**（功能层 vs 程序层 vs 物理层等混杂）。
    

📌 **根本原因：缺乏统一的抽象基准（Layer Axis）**。

---

## 四、解决方案：建立“层级轴 + 视角轴”的二维框架

|维度|说明|
|---|---|
|**层级轴（纵向）**|五层结构：应用 → 决策 → 功能 → 执行 → 支撑|
|**视角轴（横向）**|按职能区分：功能架构、模块架构、数据流架构、部署架构、演进架构|

例如：

|层级/视角|功能架构|模块架构|数据流|部署|
|---|---|---|---|---|
|应用层|BCI/MR交互|MR任务节点|用户意图流|MR设备|
|决策层|任务分发/规划|TaskManager节点|指令流|服务器|
|功能层|感知融合/SLAM|SensorFusion节点|传感器数据流|RDK|
|执行层|底盘控制|MotorDriver节点|控制量流|RDK|
|支撑层|ROS2中间件|通信适配器|DDS消息|全局|

这样你以后画架构图或写文档时：

- 想写“做什么” → 功能架构
    
- 想写“谁来做” → 模块架构
    
- 想写“怎么流” → 数据流架构
    
- 想写“在哪跑” → 部署架构  
    而层级轴保持不变，就不会乱。
    

---

## 🧠 五、你的改进建议

✅ **在文档/图表里统一采用五层架构作为主轴**（上层到下层固定顺序）。  
✅ **在每份架构图上标明“这是功能视角 / 模块视角 / 部署视角”**。  
✅ **所有组（机械/电子/软件）都沿这五层展开自己的局部架构**。

## 🧱 一、标准分层架构对照表

（适用于机器人系统 / 自主移动平台 / 智能体架构）

|层级|职责定位|典型模块|输入|输出|向上依赖|向下依赖|边界原则|
|---|---|---|---|---|---|---|---|
|**① 应用层（Application）**|定义系统目标、与人交互、任务编排|BCI接口、MR界面、上位机GUI、任务调度器|人类意图、任务命令|高层任务（TaskMsg）|无（外部输入）|决策层|不处理传感器或执行细节，只负责“想做什么”|
|**② 决策层（Decision / Planning）**|决定怎么做、何时做|行为树、任务分发节点、路径规划（Nav2 Planner）、任务策略管理|地图、状态、任务目标|执行动作计划（路径、控制策略）|应用层|功能层|不直接操作硬件或通信，只产生行为计划|
|**③ 功能层（Functional / Perception & Control）**|感知、建图、局部控制|SLAM、感知融合、避障、轨迹控制|传感器数据、决策命令|状态估计、控制量|决策层|执行层|不依赖UI或应用逻辑，不直接驱动执行器|
|**④ 执行层（Execution）**|物理动作实现、闭环控制|电机驱动、底盘节点、机械臂控制器|控制量（速度、角度）|实际运动反馈|功能层|支撑层|不做算法规划，只保证控制正确执行|
|**⑤ 支撑层（Support / Infrastructure）**|通信、系统支撑、仿真|ROS2 DDS、操作系统、中间件、驱动接口、Gazebo仿真|系统资源|系统服务|全局|硬件平台|不包含任何应用逻辑，只提供通用能力|

## ⚠️ 二、常见错误示例表与矫正建议

|错误类型|现象|原因|矫正方法|
|---|---|---|---|
|**跨层调用**|应用层直接控制底盘 / 摄像头|破坏分层独立性|所有硬件控制都应通过决策层 → 功能层 → 执行层传递|
|**逻辑混层**|把 SLAM 写进任务调度节点|混淆“功能层算法”和“决策层逻辑”|把 SLAM 独立为感知节点，仅提供地图与位姿|
|**功能重叠**|Nav2 和 TaskManager 都在规划路径|层级职责未明确|明确：Nav2 属于功能层，TaskManager 属于决策层|
|**层次遗漏**|没有明确“支撑层”，ROS通信逻辑散落各处|缺乏基础层抽象|统一把通信、驱动、仿真等归入支撑层|
|**命名混乱**|有的叫“控制层”，有的叫“算法层”|缺乏统一标准|统一采用五层术语，文档内保持一致命名|
|**图形混乱**|架构图混合模块和信号流，没有层次分界|缺乏布局规范|每层画独立矩形带，箭头只能上下流动不交叉|

## ✅ 三、你可以建立的统一分层模板（以后所有架构图都照此画）

```mermaid
flowchart TB
    subgraph L1[① 应用层]
        A1[BCI / MR 接口]
        A2[上位机 GUI]
    end

    subgraph L2[② 决策层]
        B1[任务分发节点]
        B2[路径规划器 (Nav2 Planner)]
    end

    subgraph L3[③ 功能层]
        C1[SLAM]
        C2[避障 / 感知融合]
        C3[轨迹控制器]
    end

    subgraph L4[④ 执行层]
        D1[底盘驱动]
        D2[机械臂控制]
    end

    subgraph L5[⑤ 支撑层]
        E1[ROS2 通信]
        E2[硬件驱动 / 仿真]
    end

    A1 --> B1 --> C1 --> D1
    B2 --> C2 --> D2
    C3 --> D1
    E1 -.-> C1
    E2 -.-> D1
```

## 💡 四、使用建议

- 每个文档、架构图都明确标注“本图基于五层架构标准”。
    
- 每层内部可以再细分“模块架构”、“数据流架构”，但**层间逻辑方向固定**。
    
- 团队各组（机械 / 电子 / 软件）可各自负责不同层级的细化。
