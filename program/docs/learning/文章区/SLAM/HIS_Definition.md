# 2. 建立顶层框架（Top-level Map）


太好了，这个目标很清晰。下面我给你一个**面向你当前仓库**（`ScineceTechAILab/2026-Jic_Competiion_Code`）的 **SLAM 顶层框架（H2）**，重点是“骨架结构 + 模块/接口/边界”。

## 一、SLAM 的骨架结构（Top-level Map）

**主闭环：**  
传感器输入 → 预处理与时间同步 → 状态估计(里程计) → SLAM建图定位 → 地图服务输出 → 任务/导航消费

可写成 6 层骨架：

1. **Device Layer（设备层）**  
   雷达、IMU、编码器/电机驱动、相机（可选）

2. **Driver Layer（驱动层）**  
   设备驱动节点，负责把硬件数据转 ROS2 标准消息

3. **Fusion/Odometry Layer（里程计融合层）**  
   融合编码器 + IMU，发布 `/odom` 与 `odom->base_link`

4. **SLAM Core Layer（SLAM核心层）**  
   `slam_toolbox`（2D）消费 `/scan` + `/odom`，发布 `/map` 与 `map->odom`

5. **Map Service Layer（地图服务层）**  
   地图保存/加载、地图质量评估、会话管理（mapping/localization 模式切换）

6. **Application Layer（应用消费层）**  
   Nav2、任务调度（Agent）、MR 可视化、Web 调试面板

## 三、接口设计（模块间契约）

### 1) 输入接口（SLAM前置）
- `/scan` : `sensor_msgs/LaserScan`（来自雷达驱动）
- `/imu/data` : `sensor_msgs/Imu`（来自 IMU 驱动）
- `/wheel/odom_raw` 或内部接口（来自底盘编码器）

### 2) 中间接口（状态估计）
- `/odom` : `nav_msgs/Odometry`
- `/tf` : 动态 TF（`odom->base_link`）

### 3) 核心输出（SLAM产物）
- `/map` : `nav_msgs/OccupancyGrid`
- `/tf` : 动态 TF（`map->odom`）
- `/slam_toolbox/pose`（可选）

### 4) 服务接口（地图生命周期）
- `/map/save`（封装 map_saver_cli）
- `/map/load`（切换到 localization 模式）
- `/slam/reset`（重置会话）

## 四、边界定义（Boundary）

### A. 硬件边界
**到驱动层为止**：只处理设备协议（I2C/串口/USB），不做地图逻辑。  
> 防止“硬件代码污染算法层”。

### B. SLAM边界
SLAM层只依赖标准输入（`/scan`、`/odom`、TF），不直接调用底层驱动。  
> 便于后续替换雷达/底盘。

### C. 应用边界
Nav2 / Agent / MR 只能消费 `/map`、`/tf`、定位状态，不直接改 SLAM 内部参数。  
> 避免调度层与算法层强耦合。

### D. 调试边界
Web/FastAPI 调试接口与 ROS2 Topic 解耦（通过桥接节点）。  
> 保留你当前 Web 面板优势，同时不破坏 ROS2 主数据面。

## 五、最小可运行拓扑（MVP for M1）

必须同时满足以下 4 条链路：

1. `LidarNode -> /scan`
2. `OdomNode(IMU+Encoder) -> /odom + odom->base_link`
3. `StaticTF -> base_link->laser_frame`
4. `slam_toolbox -> /map + map->odom`

只要这四条打通，你就能在 RViz 实时建图并保存地图。

# 3. 识别主流技术路线

H3 的目标不是“怎么写代码”，而是回答：  
**在可行的 SLAM 流派中，为什么我们选择这条路线，而不是其他路线。**

---

### 1) 主流范式总览（你当前场景相关）

#### 范式 A：按地图维度
- **2D SLAM**（占据栅格）
- **3D SLAM**（点云/体素）

#### 范式 B：按核心方法
- **滤波派**（EKF/Particle）
- **图优化派**（Pose Graph / Factor Graph）
- **直接法/特征法视觉派**（VO/VSLAM）

#### 范式 C：按传感器组合
- **Lidar-only**
- **Lidar + Wheel Odom**
- **Lidar + Wheel + IMU**
- **Visual(-Inertial) SLAM / Lidar-Visual Fusion**

#### 范式 D：按工程策略
- **一步到位全融合**
- **层叠式渐进集成（单传感器→双传感器→三传感器）**

---

### 2) 各路线价值取向（本质取舍）

- **精度优先**：倾向多传感器深融合、3D、复杂优化  
- **稳定交付优先**：倾向 2D + 成熟中间件 + 渐进集成  
- **研究创新优先**：倾向视觉语义融合、端到端方法  
- **工程可控优先**：倾向模块边界清晰、可调试、可回退

---

### 3) 结合你项目约束的判断（WHY）

你当前约束非常明确：
- 硬件：RPLIDAR S1 + 编码器 + BNO055 + USB相机
- 平台：RDK X5 + ROS2 Humble
- 项目属性：本科毕设 + 里程碑交付（M0~M6）
- 当前进度：驱动层已有基础，SLAM 尚未正式 ROS2 化
- 风险现实：单人开发，最怕“系统同时复杂化导致不可收敛”

因此，**最优价值选择不是“最先进”，而是“最稳可交付”**。

---

### 4) 最终路线选择（建议写入方案文档）

## 选择路线（主线）
**“2D 激光 SLAM（图优化派）+ 轮速里程计主支撑 + IMU渐进融合 + 相机后置增强”**

可对应为：
1. **阶段1**：RPLIDAR-only 打通 `/scan`
2. **阶段2**：RPLIDAR +（简化/编码器）odom 跑通 `slam_toolbox`
3. **阶段3**：加入 IMU（EKF）提升稳定性
4. **阶段4**：相机用于动态障碍/语义增强，不主导位姿

---

### 5) 为什么选这条（核心理由）

1. **与现有资产高度一致**  
   你已有雷达、编码器、IMU驱动基础，迁移成本最低。

2. **与 ROS2 生态匹配度最高**  
   `slam_toolbox + robot_localization + Nav2` 是 Humble 上最成熟组合。

3. **最符合里程碑交付逻辑**  
   先拿到“可建图可演示”，再逐步提高鲁棒性，避免大爆炸集成。

4. **可解释、可调试、可回退**  
   每层都有可观测输入输出，某一层失败不会拖垮全系统。

5. **保留创新空间**  
   后续可把相机接入语义层，服务 MR 展示与任务理解，形成差异化。

---

### 6) 明确“不选”的路线（边界声明）

- 现阶段不选 **3D SLAM 主线**：算力/标定/时间成本过高  
- 现阶段不选 **视觉SLAM主定位**：光照与纹理依赖强，调参风险高  
- 现阶段不做 **四传感器一步全融合**：集成风险过大，不符合单人开发节奏

---

### 7) 一句话 H3 结论（可直接贴PPT）

> 在本项目的硬件条件、开发周期与交付目标下，SLAM 采用“**2D 激光图优化为主、里程计渐进融合、视觉后置增强**”的工程范式。该路线在稳定性、复杂度与演示价值之间取得最优平衡，是当前阶段的理性最优解（WHY）。

## 1) 必须知道的概念（Must Know）

只保留 8 个，少一个都容易卡住：

1. **Topic 是数据总线**
   - 你至少要知道 `/scan`、`/odom`、`/map` 分别是谁发、谁用。

>**提示：odom 是里程计的意思**

2. **TF 是坐标关系树**
   - 至少要有：
     - `odom -> base_link`
     - `base_link -> laser_frame`
     - `map -> odom`（SLAM 发布）

3. **LaserScan 数据最基本结构**
   - `frame_id`、角度范围、距离数组要合法，频率要稳定。

4. **Odometry 的作用**
   - SLAM 需要运动先验；哪怕是简化 odom，也比没有强。

5. **slam_toolbox 的输入输出**
   - 输入：`/scan` + TF/odom
   - 输出：`/map` + `map->odom`

6. **RViz 最小调试法**
   - 会看 4 个显示：TF / LaserScan / Map / Odometry

7. **地图保存**
   - 会用 `map_saver_cli`，证明成果可复现。

8. **分层集成原则**
   - 先单传感器跑通，再叠加；不要三件套同时硬上。
