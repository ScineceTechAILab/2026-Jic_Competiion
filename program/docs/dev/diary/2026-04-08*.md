这些输出是 `ros2 topic hz /lidar_node/scan` 的**频率统计**，含义如下：

- `average rate: 10.034`  
  该话题平均发布频率，约 **10 Hz**（每秒约 10 条消息）。

- `min: 0.082s max: 0.116s`  
  相邻两条消息的最小/最大时间间隔（周期）。  
  对应频率大约在 $1/0.116 \approx 8.6\ \text{Hz}$ 到 $1/0.082 \approx 12.2\ \text{Hz}$ 间波动。

- `std dev: 0.00693s`  
  周期抖动的标准差，约 **6.9 ms**，数值越小说明越稳定。

- `window: 66`  
  当前统计窗口内用了 66 个样本。每次打印都会更新一次窗口统计，所以你看到多行逐步变化。

结论：这次 10 秒冒烟结果显示 `/lidar_node/scan` 基本稳定在 **10 Hz**，B3 可判定通过。

## 问题2：FastAPI 启动入口导入问题

- 【问题描述】  
  `web/main.py` 作为启动入口，原本想去启动 `web/api/main.py` 里的 FastAPI 应用，但实际运行时会失败。  
  最小复现其实就是下面这种结构：

    # main.py
    import uvicorn

    if __name__ == "__main__":
        uvicorn.run(app, host="0.0.0.0", port=8000)

    # main.py
    from fastapi import FastAPI

    app = FastAPI()

  这个例子的问题在于，main.py 里并没有正确把 `api/main.py` 的 `app` 导进来，所以入口直接报错。

- 【问题环境】  
  当前仓库里顶层目录名是 code，这会和 Python 标准库的 code 模块冲突。  
  这也是为什么 `from code.xxx import ...` 这类导入在运行时容易出问题。

- 【问题分析】  
  这个问题本质上有两层：

  1. 启动入口不完整  
  - `web/main.py` 里只有 `uvicorn.run(app, ...)`，但 `app` 没有定义或没有正确导入。

  2. 包名冲突导致导入失败  
  - 项目顶层目录叫 code，Python 可能优先解析到标准库的 code 模块，而不是你的项目目录。
  - 所以 `from code.web.api.main import app`、`from code.src...` 这类导入容易报 `ModuleNotFoundError: 'code' is not a package`。

- 【问题方案】  
  直接可行的解决方式是：

  1. 给项目根目录增加包标记  
  - 新增 __init__.py，让项目的 code 明确成为包。

  2. 统一启动入口  
  - 让 main.py 负责启动，但它只做一件事：导入 main.py 里的 `app`，然后交给 uvicorn。

  3. 统一导入路径  
  - 保持项目内部导入风格一致，避免混用容易冲突的导入方式。

- 【知识总结】  
  1. 顶层包名不要和标准库重名，尤其是 code、`json`、`logging` 这类名字。  
  2. 启动入口文件最好只负责启动，不要把大量业务逻辑放进去。  
  3. 运行时导入失败，很多时候不是代码语法错，而是包路径和 Python 解析顺序的问题。

- 【编码建议】  
  1. 如果项目结构固定，建议把顶层包名换成更具体的名字。  
  2. 保留 `__init__.py`，不要依赖太多隐式命名空间包行为。  
  3. 启动前先确保 `sys.path` 加的是仓库根，而不是子目录。  
  4. 如果以后还要拆分 `web` 和 `api`，建议用一个统一入口文件专门负责启动，不要让多个模块都直接跑 uvicorn。  

如果你要，我也可以把这个模板再整理成一版更适合放到 issue、PR 描述或者开发日报里的正式文本。

## 🔴 问题 3: WEB 页面没有显示雷达点位图

- 【**问题描述**】WEB 页面打开后 LiDAR 面板一直停留在 Waiting for scan，最小复现案例：先启动/关闭雷达节点后刷新页面，页面仍然没有点位图；排查期间 `/api/lidar` 先返回 503，后来在雷达节点启动后又因为数据序列化问题出现 500，最终导致前端拿不到可绘制的扫描快照。
- 【**问题环境**】Linux + ROS2 Humble + FastAPI + 浏览器前端 + `/lidar_node/scan` 话题。
- 【**问题分析**】这次问题的核心原因是两层链路同时有断点：一开始 WEB 端没有拿到真实发布数据，只能处于等待状态；随后即使接到 `LaserScan`，其中的 `inf` 直接透传到 JSON 也会导致接口失败。也就是说，问题不是单纯的前端画布渲染，而是**“话题发布、API 序列化、前端绘图”**三段链路里前两段都不稳定。
- 【**问题状态**】✅ 已解决
- 【**问题方案**】让 WEB 后端直接订阅 `/lidar_node/scan`，缓存最新 `LaserScan` 快照；在返回 API 之前把非有限距离转换成 `null`，确保 JSON 可序列化；前端则按照 `scan_time` 和真实有效距离做自适应缩放，保证点位落在画布内。

```python
# 订阅 ROS2 LaserScan
# 将无效距离转换为 null，避免 JSON 序列化失败
if value is None:
  ranges.append(None)
elif math.isfinite(f_value):
  ranges.append(f_value)
else:
  ranges.append(None)
```

> 【代码解读】后端负责把真实雷达话题转换成前端可消费的 JSON 快照，前端负责把扫描数据按量程自动缩放并绘制到画布里。这样做的好处是链路更清晰：只要 ROS2 发布正常，WEB 页面就能稳定显示点位图。

- 【**知识总结**】这次问题的核心原因是“订阅存在”和“数据可序列化”必须同时满足。通过这次修改，我学到了在机器人 WEB 面板里，调试顺序应该先确认话题发布是否存在，再确认接口是否能把消息安全返回，最后才检查 Canvas 是否正确绘制。
- 【**编码建议**】建议下次遇到类似问题时，先用 `ros2 topic info` 看发布者数量，再用 `curl /api/lidar` 看接口是否返回 200；如果页面仍是空白，再检查前端缩放和坐标换算是否与传感器量程一致。
